# 旧版格式兼容（AKCP 1.0 / `.aivora`）

Aivora 在 0.0.1 – 0.0.5 之间使用的配置交换格式为 **AKCP 1.0**，文件后缀 `.aivora`。AEX 1.0 上线后，该格式转为历史兼容格式，**不废弃、不迁移、不覆盖**。

## 为什么保留

1. 用户已经导出的 `.aivora` 文件必须仍能导入，凭证仍然有效。
2. 已适配 AKCP 1.0 的第三方软件不应因为 Aivora 升级而失效。
3. 强制迁移会造成用户数据丢失风险，属于不可接受的行为。

## 两种格式的区别

| 项 | AKCP 1.0（历史） | AEX 1.0（新） |
|---|---|---|
| 后缀 | `.aivora` | `.akcp` |
| Magic | `41 4B 43 50 0D 0A 1A 0A`（`AKCP`） | `41 45 58 31 0D 0A 1A 0A`（`AEX1`） |
| 头部 | 固定 64 字节二进制 | 变长 JSON + 长度前缀 |
| KDF | Argon2id（64 MiB / 3 迭代 / 并行 1） | PBKDF2-HMAC-SHA256（600000 次） |
| 密码 | AES-256-GCM | AES-256-GCM |
| 凭证 | 52 字符 Base32 | 52 字符 Base32（但派生方式不同，不可互换） |
| 批量 | 单文件可含多配置（`configs` 数组） | `profiles` 数组 |

## 识别规则

**只看 Magic，不看后缀。**

```text
前 8 字节 == 41 4B 43 50 0D 0A 1A 0A  →  AKCP 1.0
前 8 字节 == 41 45 58 31 0D 0A 1A 0A  →  AEX 1.0
其它                                  →  非法文件
```

用户把 `.aivora` 改名为 `.akcp` 时，导入方应按 Magic 判定为旧格式并走旧解密流程，或明确提示"该文件是旧版格式"。两种处理都可接受，**但不得用 AEX 参数去解旧文件后报"凭证错误"**——这是误导。

## 凭证不通用

`.aivora` 的凭证由 Argon2id 派生，`.akcp` 的凭证由 PBKDF2 派生，两种凭证：

- 长度相同（52 字符），容易被误认为一样；
- **但数学上完全不通用**，A 文件凭证解不开 B 文件。

用户从旧格式迁移到 AEX 时，需要重新获取新凭证。这是设计选择，不是兼容性缺陷。

## 保留的旧格式能力

Aivora 后续版本将继续支持：

- 导入 `.aivora` 文件（使用原凭证、原 Argon2id 参数）。
- 导出 `.aivora` 文件（作为显式选项，默认使用 AEX）。
- 全量备份 `.aivora-backup`（独立格式，不在 AEX 范围内，格式不变）。

旧格式文档见 [AKCP 目录](../../AKCP/)。
