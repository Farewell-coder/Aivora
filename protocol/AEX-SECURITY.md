# AEX Security

> 状态：1.1 已定稿，Aivora 0.0.8 起实现。1.1 移除模型列表字段，加密参数与 1.0 完全一致。

## 1. 安全模型

AEX 的安全性建立在两个前提上：

1. **凭证保密**。文件本身可以公开传递（聊天软件、网盘、U 盘），没有凭证就无法解密。
2. **AEAD 完整性**。AES-GCM 保证密文与头部被篡改时解密必然失败。

不成立的前提：

- **后缀不是安全边界**。改名为 `.json`、`.zip` 不会降低密文强度；反过来，`.akcp` 后缀也不代表文件可信。
- **源码公开不影响安全**。协议、字段、算法全部公开；安全性不依赖隐藏实现或代码混淆。
- **设备被完全控制时无保证**。已 root、被植入木马、凭证被键盘记录器捕获时，AEX 无法保护数据。

## 2. 加密参数（AEX 1.1 固定值，与 1.0 相同）

| 项 | 值 |
|---|---|
| 密码算法 | AES-256-GCM |
| 密钥派生 | PBKDF2-HMAC-SHA256 |
| 迭代次数 | 600000（合法范围 100000–2000000） |
| Salt | 16 字节 CSPRNG，每次导出重新生成 |
| Nonce | 12 字节 CSPRNG，每次导出重新生成 |
| 认证标签 | 128 bit |
| AAD | `Magic ‖ 头部长度 ‖ 头部原始 JSON 字节` |
| 密钥长度 | 256 bit |

派生公式（第三方实现必须逐字节一致）：

```
key     = PBKDF2-HMAC-SHA256(password = UTF8(normalized_credential),
                             salt     = salt_bytes,
                             iterations = 600000,
                             dkLen    = 32)
cipher  = AES-256-GCM(key, nonce, plaintext = payload_bytes, aad = aad_bytes)
```

### 2.1 凭证规范化

导入方在派生前必须对用户输入做以下规范化，顺序不可调换：

1. 去除所有空白字符（空格、制表符、换行）。
2. 去除连字符 `-`。
3. 转为大写 ASCII。

规范化后必须为 52 个 Base32 字符（字母表 `A–Z2–7`，无填充）。长度或字符集不符直接拒绝，**不得尝试部分匹配或模糊修正**。

### 2.2 参数校验

导入方在密钥派生**之前**必须完成全部参数校验，避免恶意文件用超高迭代次数做资源耗尽攻击：

- `iterations` 超出 100000–2000000 → 拒绝（`UNSUPPORTED_PARAMETER`）。
- `salt` 解码后非 16 字节、`nonce` 解码后非 12 字节 → 拒绝（`INVALID_HEADER`）。
- `tagBits` 非 128 → 拒绝。
- `kdf`、`cipher` 为未知标识 → 拒绝，不得回退到默认算法。

## 3. 密钥派生成本

600000 次 PBKDF2-HMAC-SHA256 在中等 Android 设备上约需 300–900 ms。导出与导入都必须：

- 在后台线程执行，不阻塞 UI。
- 显示"正在生成 / 正在解密"状态。
- 禁止并发触发（重复点击导致多次派生的，必须在 UI 层串行化）。

> 600000 为 1.0 固定值，已在真机实测确认可用（单次派生数百毫秒量级）。该值不得随意变更，变更需升主版本并保留旧参数支持。

## 4. 凭证生成

Aivora 参考实现使用 **256 位 CSPRNG 随机凭证**，以 RFC 4648 Base32（无填充）编码为 52 字符，展示时按 8 字符分组。

- 凭证 MUST 由密码学安全随机源生成，禁止使用时间戳、设备 ID、配置名等可推导信息。
- 凭证 MUST NOT 与配置内容建立任何派生关系。
- 每次导出 MUST 生成全新凭证；同一配置多次导出不应得到相同凭证。

## 5. 敏感数据保护

导出方 MUST：

1. 密钥只存在于加密 Payload 内，明文仅在内存中短暂存在。
2. 临时文件写入应用私有缓存目录（`Context.getCacheDir()`），不得写入公共存储。
3. 通过 FileProvider 生成 `content://` URI，禁止暴露 `file://` 真实路径。
4. 分享时授予 `FLAG_GRANT_READ_URI_PERMISSION`，且尽量使用 `Intent.createChooser` 包裹。
5. 分享结束或超时后清理临时文件。
6. 不得在日志、崩溃上报、分析 SDK 中输出凭证或明文密钥。

接收方 MUST：

1. 解密成功后自行负责明文密钥的存储安全（Aivora 使用 Android Keystore 保护的数据密钥加密后落库）。
2. 不得把明文密钥写入日志或明文配置文件。
3. 导入前展示打码预览，并由用户确认。

## 5.1 导出与分享是同一份密文

Aivora 的导出窗口提供两个动作：

- **导出**：用户自选位置，把 `.akcp` 写入本地存储。
- **分享**：把同一份 `.akcp` 写入应用私有缓存，经 FileProvider 交给系统分享面板。

两者生成的字节完全相同，加密参数一致，不产生第二种格式。区别只在交付方式。

**单条与批量必须走同一个窗口。** 批量导出不得跳过凭证展示直接拉起系统分享面板——用户看不到凭证，就无法把它交给接收方，文件等于交付失败。批量时窗口额外列出包含的配置名称，其余行为与单条一致。

两种方式都不会把凭证一并交付——凭证仍需用户另行传递。这一点在 UI 上必须显式说明，不能让用户误以为“分享出去对方就能打开”。

## 6. 用户提示

分享前必须提示：**"该文件包含完整 API Key，接收应用解密后可读取明文，请仅分享给可信应用。"**

不得使用"分享完成"暗示"目标软件已成功导入"。系统分享面板无法回报目标应用的处理结果。

## 7. 错误码

| 错误码 | 含义 |
|---|---|
| `INVALID_EXTENSION` | 扩展名不是 `.akcp` |
| `FILE_TOO_LARGE` | 超过 16 MiB |
| `INVALID_MAGIC` | 前 8 字节不匹配 |
| `INVALID_HEADER` | 头部 JSON 非法、字段缺失或长度越界 |
| `UNSUPPORTED_VERSION` | 主版本高于本地支持 |
| `UNSUPPORTED_PARAMETER` | 迭代次数、KDF、密码算法或标签长度不支持 |
| `AUTHENTICATION_FAILED` | 凭证错误或内容被篡改（不区分具体原因） |
| `INVALID_PAYLOAD` | 解密成功但 Payload 不符合 Schema |
| `WRITE_FAILED` | 导出时无法写入临时文件 |

错误信息可区分"凭证错误"与"文件损坏"，但 MUST NOT 输出明文、凭证、密钥或可用于侧信道的细节。

## 8. 深链通道（不加密，独立的安全模型）

深链（见 [AEX-DEEPLINK](AEX-DEEPLINK.md)）**不走本文 1–7 节的任何机制**：没有 PBKDF2、没有 AES-GCM、没有凭证、没有认证标签。它的安全属性与文件通道不同，必须分别理解。

### 8.1 风险

| 风险 | 说明 |
|---|---|
| 明文暴露 | 链接本身含 `apiKey` 明文，任何读到 URI 的组件都能获取密钥 |
| URI 泄漏面 | 系统日志、崩溃上报、第三方输入法/剪贴板/通知监听、`dumpsys`、屏幕录制 |
| 可伪造 | 任何人可构造链接，无签名可验 |
| 可重放 | 链接永久有效，无过期机制 |

### 8.2 缓解措施（导出方 Aivora 的责任）

1. **不落盘**：明文只在内存中停留到 `startActivity` 返回，不写文件、不写缓存。
2. **不进剪贴板**：深链按钮不复制到剪贴板，避免剪贴板监听类应用获取。
3. **不记日志**：不打印 URI、不打印 `d` 参数、不打印明文 JSON。
4. **不写导出记录**：导出记录页不留痕迹（记录本身是加密存储的，但深链本来就不需要留档）。
5. **显式选择**：必须由用户从软件列表中**主动点选**接收方，不弹系统 Sharesheet（避免误投给无关应用）。
6. **不做来源校验，也不假装做了**：文档里明确写清「任何人都能发这种链接」，接收方必须自己弹确认页。

### 8.3 接收方的责任

- 不落日志、不转存明文、展示时只显示 Key 尾 4 位、入库时用自身加密方案。
- 必须由用户确认后才写入，不得静默导入。
- 更完整的要求见 [AEX-DEEPLINK §4.5](AEX-DEEPLINK.md#45-安全与交互要求)。

### 8.4 为什么仍然提供这条通道

因为它解决的是一个明确场景：**同一台手机上两个 App 之间传配置**。此时文件通道的代价是「生成文件 → 找保存位置 → 记住 52 字符凭证 → 到对面粘贴」，用户实际会退化成手动抄 Endpoint 和 Key，安全性并不更高（甚至更低，因为会落到聊天记录里）。

深链把这一步压缩成「点两下」，代价是明文。这不是安全性的提升，是**在已知风险下的可用性取舍**。Aivora 不把它宣传为「安全传输」，并在界面与文档中明确标注「不加密」。

### 8.5 边界

如果用户需要跨设备传递、或需要给不可信的人发送配置，应当使用 `.akcp` 文件通道。深链不提供任何保密性保证。
