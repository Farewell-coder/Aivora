# AEX Changelog

协议版本独立于 Aivora 应用版本演进。此处只记录**协议规范**的变更，应用更新日志见 [README 更新日志](../README.md#更新日志)。

## 1.1 — 已定稿（Aivora 0.0.8 起实现）

**不兼容变更：移除模型列表字段。**

### 变更

- `profiles[]` 不再包含 `models` 与 `defaultModel`。接收方拿到 `baseUrl` + `apiKey` 后自行请求 `GET {baseUrl}/models` 获取模型清单。
- `protocolVersion` 由 `"1.0"` 升为 `"1.1"`。
- 版本校验采用**精确匹配**：1.1 实现拒绝 1.0 容器，返回 `UNSUPPORTED_VERSION`。
- 官方测试向量重新生成（`single.akcp` / `multiple.akcp`），密钥派生参数不变。
- `AEX-SCHEMA.json` 移除两个字段定义。

### 新增：深链导出（第二条传递通道）

- 引入 `dollhouse://aivora-import?d=<base64url>&v=1` 形式的明文链接，见 [AEX-DEEPLINK](AEX-DEEPLINK.md)。
- 深链同样**不含模型字段**，与文件通道保持一致。
- 深链不加密、不需要凭证、不写导出记录，仅支持单条配置。

### 为什么移除模型列表

1. **时效性**：模型清单随时上下线，导出瞬间的快照很快就过期，接收方拿到的是一份陈旧的名单。
2. **语义不一致**：各软件的模型命名与分组规则不同（别名、路由名、分组前缀），照搬过去制造脏数据。
3. **失败不透明**：字段存在但内容失效，接收方无法区分"用户本来就没配模型"与"配置过期了"。

改为现取现用后，接收方能拿到此刻真实可用的清单；请求失败也不阻断导入。

### 兼容性说明

- 1.1 容器在 1.0 实现上同样会被拒绝（`protocolVersion` 不匹配），这是预期行为。
- 用户升级到 Aivora 0.0.8 后，此前导出的 1.0 文件**无法导入**，需要重新导出。这是移除字段带来的必然代价，已在 [AEX-SPECIFICATION §6](AEX-SPECIFICATION.md#6-版本规则) 中明确记录。
- 接收方应**容忍**旧文件里出现 `models` / `defaultModel`，读到就忽略，不要因此报错。

## 1.0 — 已定稿（Aivora 0.0.5 起实现）

首个正式版本，Aivora 0.0.5 起实现。

- 确立 `.akcp` 作为唯一标准交换文件格式，MIME `application/vnd.aivora.akcp`。
- 容器结构：8 字节 Magic + 4 字节头部长度 + JSON 头部 + AES-256-GCM 密文。
- 加密方案：AES-256-GCM + PBKDF2-HMAC-SHA256，600000 次迭代，16 字节 Salt，12 字节 Nonce，128 位认证标签。
- 头部整体作为 AAD，防止协议版本与加密参数被篡改。
- Payload 采用 `profiles` 数组，统一承载单个、多个与全量配置。
- 定义 9 个错误码与四级兼容识别规则。

### 1.0 定稿决定

- 头部采用 JSON 序列化（非紧凑二进制），便于第三方解析与扩展。
- PBKDF2 迭代次数固定为 600000，接收方合法范围 100000–2000000。
- `apiKey` 允许为空串；`extra` 允许嵌套对象。
- 1.0 不包含发布方签名，完整性仅由 AES-GCM 认证标签保证。
- Aivora 0.0.5 起实现，导入导出双向单元测试通过。

## 1.0 补充说明（实现期）

- 导出提供“导出”（保存到本地）与“分享”（系统分享面板）两个入口，生成的文件字节一致。
- 明确凭证与文件分离：文件不携带凭证，接收方必须另行获得 52 字符凭证才能解密。
